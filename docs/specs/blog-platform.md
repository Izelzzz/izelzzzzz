# 博客平台规格

## Problem Statement

维护者需要一个可重复验证、可部署、可审查的个人博客工程。当前项目缺少统一的 CI 检查、项目入口文档和可追踪的行为规格，部署所需的 Notion 配置也依赖手工记忆。

## Solution

提供 GitHub Actions 验证流程、面向贡献者的 README 与贡献说明、公开博客行为规格，以及一个引导人工配置 Notion 集成和 GitHub Actions secrets 的向导。公开文章接口只返回属于目标数据库且不带 `私密` 标签的文章。

## User Stories

1. 作为维护者，我希望每次 Pull Request 自动执行依赖安装、代码检查和生产构建，以便在合并前发现构建问题。
2. 作为维护者，我希望推送到主要开发分支时执行同样的检查，以便持续验证分支状态。
3. 作为贡献者，我希望从 README 了解本地启动命令，以便快速运行博客。
4. 作为贡献者，我希望知道每个环境变量的用途，以便正确配置本地环境。
5. 作为部署人员，我希望知道生产环境必须配置的变量，以便完成部署。
6. 作为内容维护者，我希望公开文章列表只包含公开文章，以便私密文章不会展示给访客。
7. 作为内容维护者，我希望文章详情接口校验文章属于配置的数据库，以便外部页面标识符无法读取其他页面。
8. 作为访客，我希望首页导航可以到达介绍区域和文章区域，以便浏览网站内容。
9. 作为贡献者，我希望看到验证命令和贡献约束，以便提交符合项目要求的修改。
10. 作为新维护者，我希望向导逐步打开相关控制台并隐藏令牌输入，以便减少凭据配置错误。
11. 作为新维护者，我希望向导把本地凭据写入被忽略的 `.env.local`，以便本地开发可以读取配置。
12. 作为新维护者，我希望向导把 CI 所需凭据写入 GitHub Actions secrets，以便远程检查可以使用相同配置。
13. 作为安全审查者，我希望 CI 只读取仓库内容并使用最小权限，以便降低工作流风险。

## Implementation Decisions

- GitHub Actions 使用 Node.js 20、锁定依赖安装、ESLint 检查和生产构建作为必需检查。
- 工作流在 Pull Request、`main`、`feature/**` 和 `codex/**` 分支推送时运行，并使用并发取消减少重复运行。
- CI 不依赖真实 Notion 数据；构建只验证应用编译和静态页面生成，运行时凭据由部署平台管理。
- Notion 令牌只在服务端模块和 API 路由使用，公开接口在返回数据前执行私密标签过滤与数据库归属校验。
- README 聚焦本地开发、环境变量、检查命令和文档入口；部署细节继续由部署说明维护。
- 设置向导只持久化 `NOTION_TOKEN` 和 `NOTION_DATABASE_ID`，令牌使用隐藏输入；GitHub secrets 通过 `gh secret set` 写入。
- 规格和工单采用仓库内 `.scratch` 文档，因为当前仓库没有配置外部 issue tracker。

## Testing Decisions

- CI 测试外部行为：依赖可以按锁定版本安装、ESLint 命令成功、生产构建成功。
- Notion 公开访问测试关注公开文章、私密文章和其他数据库页面的 HTTP 可见结果，不测试内部函数调用顺序。
- 首页导航测试关注锚点最终指向的页面区域。
- 向导使用 `bash -n` 静态验证；不自动执行浏览器和凭据输入流程。
- 现有项目验证命令为 `npm run lint` 和 `npm run build`，CI 与本地贡献流程复用这两个入口。

## Out of Scope

- 不建立新的内容管理后台。
- 不改变 Notion 数据库字段结构。
- 不在 CI 中保存或生成真实 Notion 令牌。
- 不处理 Cloudflare Pages 或 Vercel 的外部部署故障。
- 不修改 Gitee 远程仓库。

## Further Notes

- `.env.example` 只包含空值示例，真实凭据必须通过本地环境或部署平台 secret 提供。
- 修改工作流时需要同步更新 README、贡献说明和设置向导中的配置说明。
